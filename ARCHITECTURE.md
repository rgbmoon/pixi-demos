## 1. Карта системы

### Пять слоёв и дирижёр

Архитектура строится из пяти слоёв, у каждого — одна зона ответственности:

| Слой                | Где живёт                                      | За что отвечает                                                                                                               |
| ------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Сетевой слой**    | [src/api/](src/api/)                           | Отправляет запросы по WebSocket, валидирует ответы. Ничего не знает про игру.                                                 |
| **Сторы (MobX)**    | [src/stores/](src/stores/)                     | Хранят состояние игры (фаза, ставка, результат) и делают его реактивным: кто читает — тот автоматически узнаёт об изменениях. |
| **Event emitter**   | [src/events/](src/events/)                     | Доставляет дискретные события («спин запрошен», «барабаны приземлились») между слоями, которые не должны знать друг о друге.  |
| **Классы анимации** | [src/game/animations/](src/game/animations/)   | Обвязка над визуальной сущностью: смысловые методы (`spin()`, `land()`), возвращающие промис «анимация закончилась».          |
| **Контроллеры**     | [src/game/controllers/](src/game/controllers/) | PIXI-контейнеры на сцене: создают анимации, подписываются на события и сторы, ловят клики.                                    |

Над слоями стоит **конечный автомат** ([src/flow/](src/flow/)) — дирижёр. Он единственный, кто знает сценарий раунда: в какой момент послать запрос, когда запустить анимацию, что записать в стор и какое событие объявить. Все остальные слои — исполнители, каждый умеет только своё.

### Поток данных

Полный перечень связей между блоками, по направлениям:

- **Сервер ↔ сетевой слой** — WebSocket. Пока роль сервера исполняет MSW-мок; сетевой код этого не знает.
- **Сетевой слой → фазы** — фаза вызывает эндпоинт (`api.sendSpin`, api приходит в контексте фазы) и получает распарсенный результат промисом.
- **Фазы → сторы** — запись состояния (`setBet`, `setPhase`, `result.run(...)`). Единственная точка записи во всей системе.
- **Фазы → эмиттер** — объявление игровых событий (`spin:started`, `spin:landed`).
- **Фазы → контроллеры** — прямые вызовы методов с ожиданием (`await reels.land(result)`): фазе нужно дождаться конца анимации, а вызов метода, в отличие от события, возвращает промис.
- **Сторы → контроллеры** — MobX-`reaction`: кнопка включается и выключается вслед за `canSpin`, никто ей не «командует».
- **Контроллеры → эмиттер** — события о действиях игрока (`ui:spinRequested`).
- **Эмиттер → фазы** — `waitFor`: фаза `idle` спит на промисе события.
- **Контроллеры → анимации** — вызовы методов (`spin` / `land` / `highlight`).

Словами: **сеть → фазы автомата → сторы + эмиттер → контроллеры → анимации**. Вверх (от картинки к логике) идут только события: контроллер сообщает «пользователь запросил спин», и на этом его знание о мире заканчивается. Вниз (от логики к картинке) автомат командует прямыми вызовами методов.

### Инварианты

Инвариант — это правило, которое должно выполняться всегда, в любой момент работы игры. Несколько таких правил держат всю конструкцию:

1. **Единственный писатель в сторы — фазы автомата.** Контроллеры, анимации и React только читают. Когда состояние меняется только из одного места, источник любого неожиданного значения находится за минуты — искать просто негде больше.
2. **Сервер — источник правды.** Клиент не вычисляет выигрыш и не «крутит» результат сам: он рисует то, что прислал сервер. В азартных играх это требование индустрии — но и вне её это дисциплинирует: клиент занимается презентацией, сервер — правилами.
3. **Событие ≠ команда.** События описывают то, что уже случилось (`ui:spinRequested`, `spin:landed`), и называются в прошедшем времени. «Сделай X» через эмиттер не передают — для этого есть прямой вызов метода.
4. **Две системы наблюдения, каждая для своего.** Эмиттер — для моментов (событие произошло и прошло). MobX — для состояния (у него есть текущее значение, которое можно спросить в любой момент). Если у «события» есть текущее значение — это состояние, его место в сторе.
5. **Граф импортов односторонний.** `game/` (контроллеры, анимации) не импортирует `flow/` (автомат). Картинка не знает про сценарий — только сценарий про картинку.

### Дерево исходников

```
src/
  api/        — WS-транспорт (service.ts) + типы транспорта + эндпоинты (root-api.ts → класс RootApi)
  events/     — типизированный эмиттер, карта событий, traceEvent, waitFor
  flow/       — движок автомата + сборка (helpers.ts) + фазы idle / spinning / result
  game/
    game-root.ts  — хост жизненного цикла игры (PIXI-init, DOM-мост, layout, порядок unbind)
    animations/   — ReelAnimation (заглушка вместо будущего Spine)
    controllers/  — ReelsController, SpinButton
    utils.ts      — waitTicks (пауза в игровом времени)
  stores/     — SpinStore (состояние раунда) + utils/ (AsyncValue, AsyncStream)
  mocks/      — MSW-моки WebSocket-сервера
  types/      — кросс-слойные типы (SpinResult, PhaseName, RequestStatus)
  constants/  — глобальные константы (environment.ts → WS_URL, tokens.ts → словарь DI-токенов, конфиг блобов фона)

  pages/, components/ — React-обвязка: страницы, UI
```

## 2. Сквозные механики

Шесть концепций, которых нет в обычном React-стеке. Каждая объясняется с нуля и сразу привязывается к коду проекта; на эти разделы опираются описания узлов в главе 3.

### 2.1 Классы и синглтоны модуля

#### Зачем здесь классы

В React-приложении состояние обычно живёт в хуках и замыканиях, а «объект» — это компонент, которым управляет React. В игровом коде так не получится: у барабанов, кнопок, транспорта и автомата своё внутреннее состояние и своё время жизни, никак не привязанное к рендеру. Класс — это способ собрать в одну единицу три вещи: **данные** (поля), **поведение** (методы) и **жизненный цикл** (конструктор создаёт, `destroy()` освобождает).

Вторая причина прозаичнее: PIXI сам построен на классах. Сцена — это дерево объектов `Container`, `Sprite`, `Graphics`, `Text`, и чтобы твой объект жил на сцене, он либо наследует `Container`, либо оборачивает его. MobX тоже удобнее всего работает с классами. То есть классы здесь — не стилистический выбор, а родной язык обеих библиотек.

#### Метод или поле-стрелка: проблема `this`

Самая частая ловушка классов в JS. У обычного метода `this` определяется **в момент вызова**, а не в момент объявления. Пока ты пишешь `button.handleTap()` — всё хорошо. Но как только метод передаётся куда-то как колбэк — `this.on('pointertap', this.handleTap)` — вызывать его будет чужой код, и `this` внутри окажется чем угодно. Поле-стрелка (`handleTap = () => {...}`) решает это: функция создаётся в конструкторе как замыкание на конкретный экземпляр, и `this` в ней привязан навсегда.

У поля-стрелки есть и второе, менее очевидное свойство — **стабильность ссылки**. Чтобы снять подписку, нужно передать _ту же самую_ функцию, что и при подписке. Именно поэтому в [GameRoot](src/game/game-root.ts) `layout` — поле-стрелка: `app.renderer.on('resize', this.layout)` при маунте и `off('resize', this.layout)` при анмаунте указывают на один и тот же объект-функцию. Если бы мы писали `on('resize', () => this.layout())`, каждый вызов создавал бы новую функцию, и отписаться было бы невозможно.

Правило проекта простое: **если функция уходит из класса наружу как колбэк — это поле-стрелка; всё остальное — обычные методы.**

#### Наследование и композиция

В проекте есть оба подхода, и граница между ними осмысленная:

- **[ReelsController](src/game/controllers/reels-controller.ts) наследует `Container`** — потому что контроллер по определению _является_ узлом PIXI-сцены: его добавляют в `app.stage.addChild(...)`, у него есть позиция, дети, `destroy()`. Наследование здесь уместно, потому что выражает правду: контроллер — это контейнер с дополнительным поведением.
- **[ReelAnimation](src/game/animations/reel-animation.ts) ничего не наследует** — у него _есть_ view (`readonly view = new Container()`), но сам он не узел сцены, а обвязка со смысловыми методами. Это композиция: внешний мир работает с методами `spin()` / `land()` / `highlight()`, а что там внутри view — `Graphics` с текстом или Spine-скелет — его не касается. Ради этой изоляции слой и существует: когда заглушку заменят на Spine, поменяется только внутренность `ReelAnimation`, а контроллер и фазы не изменятся ни на строчку.

#### Единственность экземпляра — свойство биндинга

Файл слоя экспортирует **класс**, а не готовый экземпляр. Сколько экземпляров существует и как долго они живут — решает биндинг в DI-контейнере ([2.5](#25-dependency-injection)): `defaultScope: 'Singleton'` даёт один экземпляр на контейнер, transient — новый на каждый `get()`. У каждого объекта при этом есть владелец, который знает, когда тот рождается и как умирает, — например, транспорту при выгрузке биндинга контейнер сам позовёт `disconnect()`.

Единственный экземпляр, живущий на уровне модуля, — сам `appContainer` в [app/container.ts](src/app/container.ts). Он опирается на гарантию ES-модулей: **модуль исполняется один раз**, при первом импорте, а все последующие импорты получают тот же результат. Composition root — единственная точка, где эта гарантия применяется намеренно, чтобы всё остальное могло без неё обойтись.

[GameRoot](src/game/game-root.ts) — противоположный полюс времени жизни: он забинжен transient, каждый маунт страницы получает свежий экземпляр, живущий ровно столько, сколько живёт роут. Глобального инстанса, переживающего уход со страницы, у игры нет.

### 2.2 Реактивность MobX

#### Проблема, которую решает MobX

У любого UI одна и та же фундаментальная задача: данные изменились — картинка должна обновиться. React решает её **сравнением снимков**: данные неизменяемы, `setState` создаёт новую версию, фреймворк сравнивает и перерисовывает разницу. MobX решает её **подписками на мутации**: данные изменяемы, но «прослушиваются» — каждый, кто читал значение, автоматически подписан на его изменение. Изменилось — уведомили ровно тех, кого это касается.

Этот подход называют **прозрачной реактивностью**: ты пишешь обычный императивный код — `store.bet = 20`, `if (store.canSpin) ...` — а система подписок строится сама, без единого явного `subscribe`. Для игры это особенно удобно: игровое состояние читают совсем разные потребители — PIXI-объекты, фазы автомата, в будущем React-компоненты — и все они получают реактивность одним и тем же способом, просто читая поля.

#### Четыре строительных блока

- **Observable state** — поля, за чтением и записью которых MobX следит: `phase`, `bet`, `result` в [SpinStore](src/stores/spin-store.ts).
- **Computed** — значения, выводимые из состояния: `get canSpin() { return this.phase === PhaseName.idle }`. Кешируются и пересчитываются только когда изменилось то, от чего они зависят.
- **Reactions** — побочные эффекты при изменении состояния: «когда `canSpin` изменился — включи/выключи кнопку». Реакция — конечная точка реактивной цепочки, где данные превращаются в действие.
- **Actions** — функции, которые изменяют состояние: `setBet()`, `setPhase()`.

Цепочка всегда одна: **action меняет observable → пересчитываются задетые computed → срабатывают задетые reactions**. Механика под капотом — Proxy: когда MobX запускает реактивную функцию, он записывает каждое чтение observable-поля и получает точный список зависимостей; список пересобирается при каждом запуске. Отсюда главное практическое правило: **реактивность работает только на чтении observable-полей внутри реактивного контекста**. Если прочитать значение из стора заранее и передать дальше как обычное число, реактивность на этом заканчивается.

#### Разметка декораторами: только явные аннотации

Каждый наблюдаемый член помечается декоратором **у своего объявления**, а конструктор завершает разметку вызовом `makeObservable(this)` без аргументов:

```ts
@injectable()
export class SpinStore {
  @observable phase: PhaseName = PhaseName.idle
  @observable bet = 10
  @observable.ref result = new AsyncValue<SpinResult>()  // чужой инстанс со своей разметкой — следим только за ссылкой
  @observable.ref fatalError: unknown = undefined

  constructor() {
    makeObservable(this) // обязателен: декоратор записывает разметку, применяет её этот вызов
  }

  @computed get canSpin(): boolean { ... }

  @action setPhase(phase: PhaseName) { ... }
}
```

Это **legacy-декораторы** (`experimentalDecorators`) — режим навязан inversify: его `@inject` — параметр-декоратор, который существует только в legacy, а флаг переключает интерпретацию декораторов для всего проекта. Отсюда два следствия. Первое: `makeObservable(this)` в конструкторе **обязателен** — в legacy-режиме декоратор лишь записывает разметку в метаданные класса, а превращает поля экземпляра в observable именно этот вызов; забыть его — значит получить молча нереактивный стор. Второе: современные stage-3 декораторы MobX (`@observable accessor x`, без `makeObservable`) пока недоступны — мигрируем, когда inversify освоит stage-3.

Автоматическую разметку (`makeAutoObservable`, которая размечает класс по соглашению «поля → observable, геттеры → computed, методы → actions») проект **не использует**, и причина архитектурная. Автоматика делает observable _всё_, включая то, что наблюдать не нужно, — и делает это **глубоко**: оборачивает в Proxy не только поле, но и вложенные объекты. Для тяжёлого объекта вроде PIXI `Application` это катастрофа: внутри рендерер, тикер, ссылки на WebGL-ресурсы — тысячи полей, которые никому не нужно наблюдать, а Proxy-обёртка вдобавок ломает проверки идентичности (`this.app === app` может сравнивать Proxy с оригиналом). С явной разметкой наблюдается ровно то, что помечено: **недекорированный член не наблюдается** — тяжёлый объект не утечёт в реактивность по недосмотру.

Отсюда же три частных правила:

- **`@observable.ref`** — для полей, за внутренним состоянием которых следить не нужно: DTO с сервера, `unknown`-ошибки, чужие observable-инстансы (как `result: AsyncValue` — у него своя разметка). Отслеживается только подмена ссылки. Глубокий `@observable` — для собственных примитивов и структур.
- **Приватные члены** просто не декорируются (см. `dispose` в
- Классу, в котором наблюдать нечего, MobX не подключается вовсе — поэтому в [GameRoot](src/game/game-root.ts) нет ни `makeObservable`, ни разметки: все его поля (`Application`, контроллеры, DI-контейнер) — тяжёлые нереактивные объекты.

#### Actions, транзакции и асинхронность

Требование MobX «менять состояние только в action» имеет две технические причины:

1. **Батчинг.** Все изменения внутри action накапливаются, и реакции срабатывают один раз — после завершения самого внешнего action. Без этого фаза, меняющая три поля подряд, запускала бы каждую реакцию трижды — и реакции видели бы промежуточные, несогласованные состояния.
2. **Отлов случайных мутаций.** В strict-режиме запись вне action — предупреждение. Это страховка инварианта «единственный писатель»: случайная мутация из контроллера не пройдёт незамеченной.

С асинхронностью есть тонкость, которую важно понять один раз. Action — это _синхронный_ отрезок выполнения. Когда внутри `async`-функции встречается `await`, функция приостанавливается, action заканчивается — и **всё, что после `await`, выполняется уже вне action**. Отсюда два инструмента:

- **`runInAction(() => {...})`** — обернуть кусок кода после `await` в мини-action вручную. Так делает [AsyncStream](src/stores/utils/async-stream.ts), которому значение приносит колбэк подписки.
- **`flow(function* () {...})`** — функция-генератор, где вместо `await` пишется `yield`. Генератор можно приостанавливать и возобновлять _снаружи_, поэтому MobX сам оборачивает каждое возобновление в action. Так написан [AsyncValue.run](src/stores/utils/async-value.ts):

```ts
run = flow(function* (this: AsyncValue<T>, task: () => Promise<T>) {
  this.status = RequestStatus.loading   // action
  this.error = undefined
  try {
    this.value = yield task()           // пауза; продолжение — снова action
    this.status = RequestStatus.success
  } catch (error) { ... }
})
```

Заметь: `run` — это **поле**, обёрнутое вызовом `flow()`, а не generator-метод с декоратором `@flow`. Декоратора на нём нет: обёртка уже сделана, а недекорированные члены `makeObservable(this)` не трогает. Только эта форма даёт TypeScript-тип «возвращает промис» — благодаря чему фазы могут писать `await`/`Promise.all` поверх `run`.

#### reaction: мост в нереактивный мир

PIXI-объект нельзя «перерендерить» — его свойства мутируют императивно. Для таких потребителей есть `reaction` (пакеты mobx-react/-lite и `observer()` в проекте не используются):

```ts
// SpinButton: кнопка включается и выключается вслед за фазой автомата
// (this.spinStore кнопке принёс контейнер через @inject)
reaction(
  () => this.spinStore.canSpin, // 1: что наблюдать (данные)
  (canSpin) => this.setEnabled(canSpin), // 2: что сделать (эффект)
  { fireImmediately: true } // выполнить эффект сразу, не ждать первого изменения
)
```

Первая функция — реактивная: её чтения отслеживаются, и при их изменении вызывается вторая. Вторая — обычный императивный код. `reaction` возвращает **функцию-отписку** (disposer), и [SpinButton](src/game/controllers/spin-button.ts) складывает её в массив `disposers`, чтобы снять в `destroy()`. Забытый disposer — это утечка: стор навсегда держит ссылку на мёртвую кнопку и продолжает вызывать её эффект.

`{ fireImmediately: true }` страхует от типичной ошибки: без него эффект сработает только при _первом изменении_ данных, а начальное состояние останется неприменённым — кнопка, созданная во время фазы `spinning`, оказалась бы активной.

#### Где MobX, а где нет

MobX — для **игрового** состояния (фаза, ставка, результат, позже баланс). Состояние интерфейса React (открыт ли попап, значение инпута) — обычный `useState`. И вторая граница, самая важная в проекте: MobX хранит то, у чего есть _текущее значение_. Одномоментные факты («игрок кликнул», «барабаны доехали») — не состояние, а события, и для них есть эмиттер.

### 2.3 Событийная модель

#### Паттерн publish/subscribe

Event emitter — реализация паттерна **publish/subscribe**: издатель объявляет «случилось X» всем желающим, не зная, кто его слушает и сколько их. В игре это ценно потому, что одна игровая ситуация интересна многим независимым системам: «барабаны приземлились» — это подсветка выигрыша, _и_ будущий звук, _и_, возможно, аналитика. Новый слушатель добавляется, не меняя ни строчки в источнике события.

Важная деталь механики: доставка **синхронная**. `emit()` вызывает всех подписчиков прямо сейчас, один за другим, и только потом возвращает управление — это обычный цикл по списку колбэков, ничего никуда не откладывается.

В проекте эмиттер построен на `EventEmitter` из pixi.js — это переэкспорт библиотеки eventemitter3, которая и так уже в бандле как зависимость PIXI. Ставить отдельный пакет незачем.

#### Тёмная сторона событий и как проект её гасит

Событийная связь — самая слабая связь из возможных, и в этом её сила и её опасность. Четыре классические проблемы — и ответ проекта на каждую:

**Нетипизированные payload → карта событий.** У классического эмиттера `emit(name: string, ...args: any[])` — опечатка в имени или неправильный payload обнаруживаются в рантайме. Здесь все имена и payload'ы объявлены в одном месте, [types.ts](src/events/types.ts):

```ts
export type GameEvents = {
  'ui:spinRequested': { bet: number }
  'spin:started': { bet: number }
  'spin:landed': SpinResult
}
```

Класс [GameEmitter](src/events/game-emitter.ts) параметризован этой картой, поэтому `emit('ui:spinRequsted', ...)` (опечатка) или `emit('spin:landed', { bet: 5 })` (не тот payload) — ошибки компиляции. Заодно карта отвечает на вопрос «какие вообще события есть»: вот они, все три, в одном файле.

**События-команды → правило прошедшего времени.** Соблазн: вместо вызова `reels.spin()` послать событие `reels:pleaseSpin`. Получается скрытый RPC, только хуже настоящего: нельзя дождаться завершения (emit ничего не возвращает), нельзя получить результат, нельзя узнать, услышал ли кто-то вообще. Поэтому имя события — `domain:action` в прошедшем времени: `ui:spinRequested` («спин был запрошен»), не `game:startSpin` («начни спин»). Если событие не получается назвать в прошедшем времени — это команда, и ей положен прямой вызов метода. Направление тоже фиксировано: **вверх** (view → логика) — события; **вниз** (логика → view) — вызовы методов, возвращающие промис.

**Утечки подписок → отписка как возвращаемое значение.** Подписка держит ссылку на подписчика: объект «умер», а подписка осталась — объект не соберётся сборщиком мусора, а его колбэки продолжат вызываться. У eventemitter3 `on()` возвращает сам эмиттер; обёртка меняет контракт — `on()` возвращает **функцию отписки**. Паттерн использования по всему проекту одинаковый — «мешок отписок»:

```ts
this.disposers.push(emitter.on('spin:landed', (result) => this.animation.highlight(result)))
// ...
override destroy() {
  for (const dispose of this.disposers) dispose()
  this.disposers.length = 0
  ...
}
```

Заметь: в один и тот же мешок складываются отписки эмиттера и disposers MobX-реакций — у них одинаковая сигнатура `() => void`, и `destroy()` не различает, кто есть кто.

Внутренний эмиттер закрыт (`private`) намеренно: у голого eventemitter3 есть `off(event)` без колбэка и `removeAllListeners()`, которые снимают **чужие** подписки. Один такой вызов из любого места — и молча отваливаются слушатели в другом конце проекта. Обёртка просто не даёт до них дотянуться.

**Невидимый граф вызовов → трассировка и счётчики.** По вызову метода можно провалиться в определение; по `emit` — нельзя: подписчиков пришлось бы искать текстовым поиском. В DEV-сборке каждый `emit` логируется в консоль (`[event] ui:spinRequested {bet: 10}`) — это главный инструмент отладки: по консоли видна точная последовательность моментов раунда. А `listenerCounts()` возвращает число подписчиков по каждому событию: если числа растут от раунда к раунду — кто-то не вызывает свою отписку.

#### waitFor: событие как промис

[waitFor](src/events/helpers.ts) — маленькая утилита с большой ролью: она превращает «подписаться и ждать одно событие» в промис:

```ts
const { bet } = await waitFor(emitter, 'ui:spinRequested', { signal })
```

Именно на ней стоит конечный автомат: фаза `idle` не крутится в цикле, опрашивая флаги, — она **спит на промисе**, пока событие не придёт. Внутри waitFor три необязательных механизма, каждый закрывает свой сценарий:

- **`signal` (AbortSignal)** — отмена извне. Игрок ушёл со страницы — автомат абортит сигнал, и висящий waitFor реджектится, вместо того чтобы жить вечно и держать подписку.
- **`timeoutMs`** — сторожевой таймер на случай «событие не пришло никогда». Это одно из двух легальных применений `setTimeout` в проекте: сторож и _должен_ идти по системному времени, чтобы сработать даже в свёрнутой вкладке (подробнее — в [2.6](#26-pixi-и-мост-с-react)).
- **`filter`** — ждать не любое событие, а подходящее: пригодится, когда барабанов станет пять и нужно будет дождаться остановки конкретного.

Реализация использует приём **settle**: все три источника исхода — подписка, abort и таймер — складывают свои функции очистки в общий список, и тот, который сработал первым, снимает все три разом. Промис одноразовый: после первого подходящего события waitFor полностью убирает за собой.

### 2.4 Конечный автомат

#### Проблема: состояние, размазанное по флагам

Представь раунд слота без автомата. Появляются флаги: `isSpinning`, `hasResult`, `isShowingWin`, `canClick`… Каждый новый механизм добавляет флаг, и число _комбинаций_ растёт как 2ⁿ. Осмысленных комбинаций при этом единицы — но код вынужден защищаться от всех: `if (isSpinning && !hasResult && ...)`. Рано или поздно какая-то пара флагов оказывается в сочетании, которое никто не предусматривал, и игра зависает в состоянии, у которого даже нет названия.

**Конечный автомат** (finite state machine, FSM) — прямой ответ: есть **конечный набор именованных состояний** (в каждый момент активно ровно одно), есть **явные переходы**, а всё, что не описано, — **невозможно**. Вместо восьми комбинаций флагов — три явных состояния: `idle` (ждём игрока), `spinning` (крутимся и ждём сервер), `result` (показываем результат). На вопрос «что сейчас происходит в игре?» всегда есть односложный ответ, и это же значение лежит в сторе (`spinStore.phase`), управляя кнопкой.

Реализация — собственный движок в ~50 строк ([fsm.ts](src/flow/fsm.ts)) на **async-фазах**: состояние — это `async`-функция, которая выполняется, пока состояние активно, «спит» на `await` в ожидании событий и анимаций, и завершается, возвращая имя следующего состояния. Готовые statechart-библиотеки (XState и подобные) не взяты сознательно: раунд слота — по природе _линейный асинхронный сценарий_ («дождись клика → запусти сеть и анимацию → покажи результат → сначала»), и async/await выражает его буквально, без отдельного языка описания переходов. Плюс учебная цель: свой движок показывает механику без чёрного ящика.

#### Устройство движка

Фаза — это объект с именем и async-функцией входа:

```ts
export type Phase = {
  readonly name: PhaseName
  enter(context: PhaseContext): Promise<PhaseName> | PhaseName // возвращает имя следующей фазы
  exit?(context: PhaseContext): void
}
```

Движок — цикл, который крутит фазы:

```ts
async start(): Promise<void> {
  let next = this.initial
  while (!this.controller.signal.aborted) {
    const phase = this.phases[next]
    this.onPhaseChange?.(phase.name)
    try {
      next = await phase.enter(this.context)
    } catch (error) {
      if (this.controller.signal.aborted) return  // отмена — не ошибка
      this.onError?.(error)
      return
    } finally {
      phase.exit?.(this.context)
    }
  }
}
```

Здесь два неочевидных решения, и оба важные.

**Переход — это `return`, а не вызов.** Фаза не переключает автомат сама (никакого `fsm.goTo('result')` изнутри) — она _возвращает_ имя следующей фазы, а переключает движок. Во-первых, так граф переходов читается прямо по `return`-ам фазы: открой [spinning.ts](src/flow/phases/spinning.ts) — и видно, что из `spinning` можно уйти в `result` или (при ошибке) в `idle`, и больше никуда. Во-вторых, это защита от незаметной утечки: если бы фазы вызывали друг друга (`idle` → `await spinning()` → `await result()` → …), каждый раунд наращивал бы цепочку вложенных незавершённых промисов — стек рос бы бесконечно. Цикл `while` держит глубину постоянной: фаза завершилась, промис закрылся, следующая итерация.

**Внутри фазы нет циклов.** Появился `while` внутри `enter` — значит, фаза на самом деле состоит из двух состояний, и их надо разделить. Это правило дисциплины: автомат полезен ровно настолько, насколько полно состояния вынесены на его уровень.

`exit` вызывается в `finally` — то есть гарантированно, даже если фаза упала или была отменена. Сейчас ни одна фаза `exit` не использует, но место для очистки при выходе из фазы уже предусмотрено.

Тонкость, которую стоит держать в голове: при фатальной ошибке (не отмене) движок вызывает `onError` и **выходит из цикла** — автомат останавливается до следующего маунта страницы. Ошибка записывается в `spinStore.fatalError`, но пока её никто не читает; фаза в сторе остаётся последней активной, поэтому `canSpin === false` и кнопка выключена без какой-либо индикации для игрока.

#### Отмена: один AbortController на всю игру

Движок создаёт `AbortController` и кладёт его `signal` в контекст фаз. Дальше сигнал протекает всюду, где что-то ждут: `waitFor(emitter, 'ui:spinRequested', { signal })`, `reels.spin(signal)`, `waitTicks(ticker, ms, signal)` — и даже в сетевой запрос (`api.sendSpin(bet, signal)`).

`fsm.dispose()` (вызывается при анмаунте страницы) делает `controller.abort()` — и **все висящие ожидания реджектятся разом**: спящий waitFor, недокрученная анимация, пауза на тикере, сетевой запрос. Исключение долетает до `catch` в движке, тот видит `signal.aborted` и молча выходит. Ни одна фаза не переживает уход со страницы, ни одна подписка не остаётся висеть.

Это стандартный современный паттерн сквозной отмены (тот же, что у `fetch`), и стоит запомнить его форму: **создаёт controller тот, кто владеет жизненным циклом; все, кто ждёт, принимают signal**.

#### Параллельность внутри фазы

Фаза `spinning` запускает сеть и анимацию **одновременно**:

```ts
await Promise.all([spinStore.result.run(() => api.sendSpin(bet, signal)), reels.spin(signal)])
```

Барабанам незачем ждать сервер: они начинают крутиться в момент клика, а ответ приходит, пока они крутятся. `Promise.all` ждёт обоих. Если сервер быстрый (а мок — быстрый), фаза всё равно не закончится раньше, чем анимация докрутит свои 900 мс. Если сервер медленный — анимация докрутит, остановится, и фаза продолжит ждать один только ответ; визуально это «барабаны замерли на случайных символах» — приемлемо для заглушки, а в настоящем слоте на этот случай делают анимацию бесконечного вращения до прихода результата.

### 2.5 Dependency Injection

#### Идея

Dependency Injection (внедрение зависимостей) — принцип, звучащий страшнее, чем он есть: **модуль не добывает свои зависимости сам — их ему приносят**. «Добывает сам» — это когда класс внутри себя пишет `import { gameEmitter }` или `new ReelAnimation()`, намертво привязываясь к конкретной реализации. «Приносят» — это когда зависимость приходит параметром:

```ts
// ReelsController не знает, ЧЕЙ это тикер и ЧЕЙ эмиттер — ему принесли, он пользуется
constructor(ticker: Ticker, emitter: GameEmitter<GameEvents>) { ... }
```

Сам механизм передачи остался прежним, в двух формах:

- **Через конструктор** — для объектов: `ReelsController(ticker, emitter)`, `SpinButton(emitter, spinStore)`, `new ReelAnimation(ticker)`.
- **Через объект-контекст** — для функций: каждая фаза получает `PhaseContext` со всем необходимым — `{ emitter, reels, spinStore, api, signal }`. Это тот же DI, просто зависимости собраны в один параметр, потому что их несколько и у всех фаз набор одинаковый.
- **Кто вызывает конструкторы**: это делает DI-контейнер [inversify](https://inversify.io/), а не ручной код.

#### Что это даёт

**Подменяемость.** Раз `ReelsController` принимает _любой_ объект с интерфейсом `GameEmitter<GameEvents>`, в тесте ему можно дать свежий изолированный эмиттер. Фазе можно дать фейковый `reels`, у которого анимации завершаются мгновенно, — и проверить логику переходов без канваса и таймеров вообще. С контейнером подмена становится вопросом одного биндинга: потребители не меняются.

**Явность.** Сигнатура конструктора — это честный список того, от чего объект зависит. Скрытых связей нет: если в конструкторе `SpinButton` нет сети — значит, кнопка гарантированно не ходит в сеть.

**Односторонний граф импортов.** `PhaseContext` содержит `reels: ReelsController` — фазы _пользуются_ контроллером, но `game/` при этом не импортирует `flow/`. Зависимость направлена в одну сторону на уровне типов и файлов, и ESLint-правило `import/no-cycle` никогда не сработает.

**Управляемое время жизни.** У каждого объекта ровно один владелец — контейнер (или, для рантайм-значений, их создатель). Кто создал — тот и уничтожает.

#### DI-контейнер: словарь токенов, биндинги, скоупы

Контейнер — это реестр рецептов: «по такому-то идентификатору выдай такой-то объект». Три понятия:

- **Токен** — идентификатор зависимости. TypeScript-интерфейсы в рантайме не существуют, поэтому токен — это `Symbol`, типизированный через `ServiceIdentifier<T>`. Все токены проекта объявлены в одном словаре [constants/tokens.ts](src/constants/tokens.ts) — `TOKENS` для зависимостей — то же, что карта `GameEvents` для событий: единственное место имён, компилятор проверяет соответствие типов. В рантайме файл — лист графа импортов (только `Symbol(...)`, типы через `import type`), поэтому слои импортируют его без риска циклов.
- **Биндинг** — рецепт создания: `bind(TOKENS.SpinStore).to(SpinStore)` («создай класс, разреши его @inject-параметры»), `toDynamicValue(() => ...)` («вызови фабрику»), `toConstantValue(x)` («отдай готовое значение»).
- **Скоуп** — время жизни: singleton (один экземпляр на контейнер, кешируется) или transient (новый на каждый `get`). Оба контейнера проекта сконфигурированы `defaultScope: 'Singleton'` — осознанное отличие от дефолта inversify: в этом графе всё одноэкземплярное, а случайно-транзиентный стор дал бы трудноловимый баг (кнопка и автомат с _разными_ сторами). Transient задаётся явно и только там, где нужен (GameRoot).

Зависимости объявляются декораторами: `@injectable()` на классе, `@inject(TOKENS.X)` на каждом параметре конструктора. Токены **всегда явные**: `emitDecoratorMetadata` выключен (инъекция «по типу параметра» не работает и не нужна — явный токен читается однозначно), поэтому классы зависимостей потребитель импортирует только как типы. Правило выбора рецепта:

- зависимости — сервисы → `@injectable`/`@inject` + `.to(Class)` (RootApi, SpinStore, контроллеры, GameRoot);
- у класса конфиг, дженерик или это сборка агрегата → фабрика `toDynamicValue`, без декораторов; конфиг живёт в композиции, а не в классе (`new WsTransport({ url: WS_URL })`, `new GameEmitter<GameEvents>(traceEvent)`, `createGameFsm({...})`);
- значение создано вне контейнера (PIXI `Application`, `Ticker`) → `toConstantValue`: контейнер его «одалживает», а уничтожает создатель.

#### Composition root: два контейнера

Если все только принимают зависимости — кто-то должен объявить рецепты. Это место называется **composition root** (корень сборки); в проекте он живёт в `app/` и состоит из двух контейнеров с разным временем жизни:

- **[app/container.ts](src/app/container.ts)** — app-уровень, живёт всё время работы вкладки: `WsTransport`, `RootApi`, `GameEmitter`, `SpinStore`, транзиентный `GameRoot` и фабрика game-контейнера. Единственный module-scope синглтон проекта — сам `appContainer`.
- **[app/game-container.ts](src/app/game-container.ts)** — game-уровень, дочерний контейнер (`new Container({ parent })`) на один маунт страницы: константы `Application`/`Ticker`, контроллеры, автомат. Child видит биндинги родителя (контроллерам достаются app-эмиттер и стор), но его собственный кэш синглтонов умирает вместе с ним при анмаунте. Отсюда поведение: ставка в сторе переживает уход со страницы (app-уровень), а игровой граф каждый раз собирается заново (game-уровень).

`container.get()` разрешён только в точках входа: в `app/` (сам корень) и на роут-страницах (`GamePage` резолвит `GameRoot`). Слои о контейнере не знают — они видят только конструкторы и `TOKENS`. Разорвана и единственная петля композиции: `GameRoot` получает фабрику game-контейнера инъекцией (`TOKENS.GameContainerFactory`), а не импортом `container.ts`, — иначе `container.ts → game-root.ts → container.ts` замкнулся бы в цикл.

#### Жизненный цикл через контейнер

Контейнер владеет не только рождением, но и смертью: у биндинга есть `onDeactivation` — обработчик, который вызывается при `unbind` и объявляется **рядом с `bind()`**: как объект умирает, написано там же, где как он рождается (автомату — `dispose()`, контроллерам — `destroy()`, транспорту — `disconnect()`).

Одного контейнер не гарантирует — **порядок** деактиваций при массовом `unbindAll()`. А PIXI-teardown порядкозависим: автомат нужно погасить раньше контроллеров, которые он дёргает. Поэтому порядок остаётся явным кодом — цепочка синхронных `unbind()` в `GameRoot.unmount()`, единственном месте, где он важен. Все деактивации синхронные — этого требует синхронный `unbind` (появится async-очистка — соответствующий вызов меняется на `unbindAsync`). Полный каскад — в [главе 5](#5-жизненный-цикл-маунт-и-анмаунт-игры).

### 2.6 PIXI и мост с React

#### Что такое PIXI и чем он не React

PIXI.js — 2D-рендерер поверх WebGL/WebGPU. Он делает одно: очень быстро рисует дерево объектов в `<canvas>`. Ни состояния, ни данных, ни архитектуры он не навязывает — всё это приносишь сам (у нас: MobX, эмиттер, автомат).

Главное отличие от React — модель работы с деревом. В React ты описываешь, как интерфейс должен выглядеть, а фреймворк сам приводит DOM к этому описанию. PIXI устроен иначе — это **удерживаемая сцена** (retained mode): ты один раз строишь дерево объектов, а дальше **мутируешь** их свойства: `label.text = '3 3 3'`, `background.alpha = 0.4`, `sprite.position.set(x, y)`. Рендерер каждый кадр отрисовывает текущее состояние дерева. Никакого diff и перерендеров: объект живёт, пока его явно не уничтожили, меняются только его поля.

#### Application и сцена

`Application` — сборка всего необходимого: **renderer** (рисует), **stage** (корневой контейнер сцены), **ticker** (цикл кадров), **canvas** (DOM-элемент). В PIXI v8 инициализация асинхронная:

```ts
const app = new Application()
await app.init({ background: '#475569', resizeTo: container }) // async: выбор и настройка GPU-бэкенда
container.appendChild(app.canvas) // canvas вставляем в DOM сами
```

Сцена — дерево. Узлы — наследники `Container`: контейнер группирует детей, трансформации (позиция, поворот, масштаб, прозрачность) действуют каскадно на всё поддерево, порядок детей определяет порядок отрисовки. Листья дерева в проекте: **`Graphics`** (векторные фигуры с цепочечным API — фон кнопки и табло), **`Text`** (символы барабанов, надпись SPIN), **`Sprite` + `Texture`** (картинка; пока используется только в фоне лендинга).

Ввод устроен привычно: у объекта включается интерактивность `eventMode = 'static'`, и он получает события вроде `pointertap` — PIXI сам вычисляет по координатам, в какой объект сцены попал указатель. Ресайз — через опцию `resizeTo: container`: рендерер сам следит за размером контейнера, при изменении эмитит `resize`, на который [GameRoot](src/game/game-root.ts) вешает `layout()` — пересчёт позиций контроллеров. Ручных `ResizeObserver` в игровом коде нет.

#### Ticker: игровое время

`app.ticker` — цикл кадров на основе `requestAnimationFrame`. Функция, добавленная через `ticker.add(fn)`, вызывается каждый кадр и получает сам тикер, у которого есть `deltaMS` — сколько миллисекунд прошло с прошлого кадра. Всё движение в проекте — накопление `deltaMS`: мерцание символов в [ReelAnimation](src/game/animations/reel-animation.ts), дрейф блобов в фоне лендинга.

Здесь живёт самое важное правило проекта про время. У браузера **два времени**: системное (`setTimeout`, идёт всегда) и кадровое (`requestAnimationFrame`, останавливается в свёрнутой вкладке). Анимации живут в кадровом времени. Если игровую задержку сделать на `setTimeout`, то в свёрнутой вкладке произойдёт рассинхрон: тикер стоит, картинка заморожена, а `setTimeout` честно отсчитал 900 мс — и автомат уехал в следующую фазу. Игрок возвращается на вкладку: результат уже «показан», хотя барабаны не сделали ни кадра.

Поэтому игровые паузы — только через [waitTicks](src/game/utils.ts): промис, который резолвится, когда _тикер_ накопил нужные миллисекунды. Вкладка свёрнута — тикер стоит — пауза честно замирает вместе с картинкой. `setTimeout` в проекте легален ровно в одной роли: **сторожевой таймер** (watchdog) на сетевые ответы и события ([service.ts](src/api/service.ts), [waitFor](src/events/helpers.ts)) — сторож обязан сработать по системному времени, даже когда вкладка свёрнута.

#### Уничтожение: GPU-ресурсы не убирает сборщик мусора

Текстуры, буферы и WebGL-контекст живут на стороне GPU, и JS-сборщик мусора про них не знает. Всё, что создано, нужно уничтожать явно: `app.destroy(true, { children: true })` — снести приложение, канвас и всех детей сцены. В проекте выстроена дисциплина владения: **кто создал — тот уничтожает**. `GameRoot` владеет `Application` и контроллерами; контроллер владеет своими подписками (мешок disposers) и — как родитель в дереве сцены — view анимации, который уничтожится вместе с ним через `children: true`.

#### Мост React ↔ PIXI

React и PIXI не смешиваются: React управляет DOM-страницей, PIXI — содержимым одного `<canvas>`. Мост между ними — один компонент и один канон ([GamePage](src/pages/game/index.tsx)):

```tsx
export const GamePage = () => {
  const containerRef = useRef<HTMLDivElement>(null)

  useEffect(() => {
    const container = containerRef.current
    if (!container) return

    const game = appContainer.get(TOKENS.GameRoot) // transient: свежий хост на каждый маунт
    void game.mount(container) // построить весь PIXI-мир внутри div
    return () => game.unmount() // и полностью снести его при уходе
  }, [])

  return <div ref={containerRef} className="w-full h-full" />
}
```

React отдаёт PIXI пустой `div` и обещает позвать cleanup при уходе со страницы — на этом их взаимодействие заканчивается. Дальше миры не пересекаются: React не знает, что внутри канваса, PIXI не знает, что он внутри React-роута.

Единственная тонкость — **StrictMode**. В dev-режиме React монтирует эффекты дважды: mount → cleanup → mount. А `app.init()` асинхронный — и получается гонка: первый `mount` ещё ждёт `init`, а его уже отменили и запустили второй. Без защиты на странице окажутся два канваса, один из которых — осиротевший.

Защита в [GameRoot](src/game/game-root.ts) — поле `pending`, «токен актуальности»:

```ts
const app = new Application()
this.pending = app          // я — актуальная попытка маунта
await app.init({ ... })     // ← за время этого await всё могло измениться
if (this.pending !== app) { // пока я ждал, случился unmount (pending=null) или новый mount
  app.destroy(true, { children: true })  // я устарел: уничтожаю СВОЁ и молча выхожу
  return
}
```

`unmount()` ставит `pending = null` — и любой недоехавший `mount` после своего `await` сам увидит, что устарел. Тот же приём в функциональном виде — локальный флаг `disposed` в [pages/main/utils.ts](src/pages/main/utils.ts). Общий принцип запомни как «**проверь актуальность после каждого await**»: асинхронная инициализация + внешняя отмена всегда требуют такой проверки.

## 3. Узлы: модули по одному

Порядок — снизу вверх по стеку: сначала сеть и её мок, потом события и автомат, затем состояние, картинка и сборка. Механика из главы 2 здесь не повторяется — только устройство конкретных файлов и неочевидные решения в них.

### 3.1 api — сетевой слой

**[service.ts](src/api/service.ts)** — WebSocket-транспорт, ядро сетевого слоя. Это класс `WsTransport` с тремя публичными методами — `request`, `subscribe`, `disconnect`; состояние (сокет, карта ожидающих запросов `pending`, карта push-подписчиков `listeners`) — в приватных полях. Экземпляром владеет app-контейнер (биндинг-фабрика в [app/container.ts](src/app/container.ts)); свободных обёрток вида `export const { request } = transport` не выносим — деструктуризация метода оторвала бы его от `this`. Конфиг в класс не зашит: `url` — обязательное поле опций, `WS_URL` подставляет биндинг, так что транспорт ничего не знает про environment. Типы транспорта (опции, записи `pending`/`listeners`) вынесены в соседний [types.ts](src/api/types.ts).

WebSocket — это просто двусторонний канал сообщений: в отличие от HTTP, встроенного понятия «запрос и ответ на него» в нём нет. Транспорт достраивает его до двух нужных игре моделей общения:

**Запрос-ответ** — через конверт (envelope) и сопоставление ответа с запросом по id. Каждое сообщение — JSON вида `{ id?, type, payload, error? }`. Отправляя запрос, транспорт генерирует id через `nanoid()` (не счётчик — id должен быть уникален и между вкладками), создаёт «отложенный» (deferred) промис, кладёт его `resolve`/`reject` в карту `pending` под этим id, шлёт `{ id, type: 'spin', payload }` и возвращает промис вызывающему. Когда с сервера приходит сообщение **с id**, транспорт находит в `pending` соответствующую запись, валидирует payload zod-схемой запроса и резолвит промис. Это единственное место в проекте, где легален «сырой» `new Promise` с внешним resolve: промис резолвится не изнутри своего тела, а из обработчика чужого события — `async/await` такое выразить не может.

Три механизма защищают запрос от вечного ожидания:

- **Сторожевой таймер**: не пришёл ответ за 10 секунд — запись удаляется из `pending`, промис реджектится. Без него потерянный сервером ответ означал бы вечно висящий `await` в фазе.
- **Ответ-ошибка**: конверт с полем `error: { code, message }` реджектит промис сразу, не дожидаясь таймаута.
- **Отмена извне**: четвёртым аргументом `request` принимает `{ signal }` — тот же `AbortSignal`, которым автомат гасит анимации. У каждого запроса внутри свой `AbortController` (`lifetime`): одна функция `dispose()` снимает и таймер, и слушателей сокета разом, каким бы способом запрос ни завершился. При закрытии сокета все незавершённые запросы реджектятся скопом (`rejectAllPending`).

**Push-подписки** — сообщение **без id** (или с id, которого нет в `pending`) раздаётся подписчикам, зарегистрированным в карте `listeners` на его `type`: у каждого подписчика своя zod-схема и колбэк, `subscribe()` возвращает функцию отписки. Это серверная инициатива — сообщения, которые никто не запрашивал.

Обработчик входящих сообщений — **граница без страховки сверху**: у WS-колбэка нет внешнего обработчика исключений, упавший разбор оборвал бы обработку молча. Поэтому каждый шаг защищён по месту: `JSON.parse` обёрнут в `try/catch`, конверт разбирается через `safeParse` (невалидное сообщение игнорируется без ошибки), а каждый push-подписчик вызывается в собственном `try/catch` — исключение в одном обработчике не лишает сообщения остальных.

Ещё две детали:

- **Переподключение уже встроено.** Сокет — `ReconnectingWebSocket` из библиотеки partysocket: при обрыве он сам переподключается с нарастающей задержкой. Транспорту остаётся только реджектить незавершённые запросы при `close`.
- **Ленивое подключение + ожидание открытия.** Сокет создаётся при первом `request`/`subscribe`, а не при старте приложения. `whenOpen` решает гонку «запрос отправлен раньше, чем сокет открылся»: если сокет ещё не открыт, отправка ждёт события `open`.

**[root-api.ts](src/api/root-api.ts)** — образец модуля-эндпоинта, по которому будут писаться остальные: zod-схема ответа + класс-фасад с методами игровой семантики:

```ts
const SpinResultSchema = z.object({ symbols: z.array(z.number()), win: z.number() })

@injectable()
export class RootApi {
  private readonly transport: WsTransport

  constructor(@inject(TOKENS.WsTransport) transport: WsTransport) {
    this.transport = transport
  }

  sendSpin(bet: number, signal?: AbortSignal): Promise<SpinResult> {
    return this.transport.request('spin', SpinResultSchema, { bet }, { signal })
  }
}
```

Класс вместо свободных функций — чтобы транспорт приходил через конструктор, а не импортом: потребители (фазы) получают `api` из контекста и не привязаны к конкретному экземпляру.

Схема здесь — не формальность: это граница доверия. Всё, что пришло из сети, — `unknown`, пока zod не подтвердил форму. Дальше по коду `SpinResult` можно передавать без единой проверки — типам можно верить, потому что на входе стоит валидатор.

Две тонкости, которые легко забыть:

- Тип `SpinResult` объявлен руками в [types/game.ts](src/types/game.ts), а схема — отдельно здесь; совпадают они только благодаря структурной типизации возврата `request`. Меняешь одно — меняй и второе: связи «схема ↔ тип» на уровне объявления нет.
- `WS_URL` ([constants/environment.ts](src/constants/environment.ts)) отдаёт `import.meta.env.VITE_WS_URL` как есть, без валидации: если переменной нет в `.env.local`, биндинг передаст транспорту `undefined`, тот попробует открыть сокет на нём — и ошибка проявится далеко от своей причины.

### 3.2 mocks — фальшивый сервер

Бэкенда у проекта нет — его роль исполняет [MSW](https://mswjs.io/) (Mock Service Worker). Ключевое свойство MSW: перехват происходит **на сетевом уровне**, через Service Worker браузера. Приложение об этом не знает — `service.ts` открывает настоящий WebSocket на настоящий URL, и весь сетевой код прогоняется по-настоящему. Когда появится реальный бэкенд, в `src/api/` не придётся менять ни строчки.

**[create-ws-handler.ts](src/mocks/create-ws-handler.ts)** — базовая обвязка: слушает подключения к `url`, парсит входящие сообщения и по полю `type` направляет каждое в свой обработчик из карты `endpoints`. Эндпоинт получает две функции ответа: `reply(type, payload)` — успешный ответ, и `fail(code, message)` — конверт с полем `error`, который транспорт на клиенте превращает в реджект запроса. Обе сами подставляют в ответ **id из запроса** — так мок сохраняет связь «запрос → ответ», которую ждёт транспорт. Контекст подключения (`push` — отправить клиенту сообщение без запроса, `onClose` — очистить ресурсы при отключении) существует под будущие push-рассылки; текущим эндпоинтам он не нужен. Типы обвязки — в соседнем [types.ts](src/mocks/types.ts).

**[handlers.ts](src/mocks/handlers.ts)** — сами «серверные» правила. Эндпоинт `spin`: сгенерировать три случайных символа (0–4), посчитать выигрыш (все три совпали → ставка × 10), ответить `spinResult`. Обрати внимание — **выигрыш считает мок**, то есть «сервер». Клиент в [result-фазе](src/flow/phases/result.ts) и [highlight](src/game/animations/reel-animation.ts) только читает `win`, ничего не пересчитывая: инвариант «сервер — источник правды» соблюдается даже в игрушечном моке.

**[browser.ts](src/mocks/browser.ts)** + [main.tsx](src/main.tsx): worker собирается из хендлеров, а запускается только в DEV и через динамический `import()` — в прод-бандл MSW не попадает вовсе. React рендерится строго **после** `worker.start()`: иначе первый же запрос успел бы уйти в сеть до того, как перехватчик заработал.

### 3.3 events — событийный слой

Четыре файла, вся механика разобрана в [2.3](#23-событийная-модель):

- [types.ts](src/events/types.ts) — карта `GameEvents` (единственное место, где заводятся имена событий) и служебные типы `EventMap`/`EventName`.
- [game-emitter.ts](src/events/game-emitter.ts) — класс `GameEmitter`; единственный экземпляр создаёт app-контейнер (фабричный биндинг: класс generic-параметризован картой событий).
- [utils.ts](src/events/utils.ts) — `traceEvent`, DEV-логгер событий; существует только в DEV-сборке и передаётся в конструктор эмиттера биндингом в [app/container.ts](src/app/container.ts). Это единственное легальное место `console.*` в проекте.
- [helpers.ts](src/events/helpers.ts) — `waitFor`, мост «событие → промис».

Одна деталь реализации, которую стоит понимать при чтении `game-emitter.ts`: внутренний eventemitter3 типизирован нарочито широко (payload как `unknown`), потому что через его собственные дженерики нашу карту событий выразить не удаётся. Вся типобезопасность обеспечивается сигнатурами `on`/`emit` обёртки, а два неизбежных каста заперты внутри класса — наружу `unknown` не течёт.

### 3.4 flow — конечный автомат раунда

Структура слоя: [types.ts](src/flow/types.ts) — контракты `Phase`, `PhaseContext` и опций; [fsm.ts](src/flow/fsm.ts) — движок (разобран в [2.4](#24-конечный-автомат)); [helpers.ts](src/flow/helpers.ts) — сборка `createGameFsm`: словарь из трёх фаз, стартовая — `idle`. Сами фазы — по файлу на состояние в `phases/`.

Все зависимости фаз — включая `spinStore` и `api` — приходят через `PhaseContext`: фазы не импортируют ничего, кроме типов и констант, а чем их укомплектовать, решает биндинг автомата в [app/game-container.ts](src/app/game-container.ts).

**[idle.ts](src/flow/phases/idle.ts)** — ожидание игрока. Вся фаза — три строки: заснуть на `waitFor(emitter, 'ui:spinRequested', { signal })`, по пробуждении записать ставку в стор (`spinStore.setBet(bet)`), вернуть `spinning`. Пока фаза спит, игра полностью пассивна — ни проверок в цикле, ни таймеров.

**[spinning.ts](src/flow/phases/spinning.ts)** — сеть + анимация параллельно:

```ts
enter: async ({ emitter, reels, spinStore, api, signal }) => {
  const { bet } = spinStore
  emitter.emit('spin:started', { bet })
  await Promise.all([spinStore.result.run(() => api.sendSpin(bet, signal)), reels.spin(signal)])
  if (spinStore.result.status === RequestStatus.error) {
    return PhaseName.idle
  }
  return PhaseName.result
}
```

Три вещи, которые легко не заметить. Первое: `spin:started` сейчас никто не слушает — событие объявлено на вырост (звук запуска, счётчик статистики подпишутся, не трогая фазу). Второе: `Promise.all` не упадёт из-за сети — `AsyncValue.run` не реджектится (см. [3.5](#35-stores--состояние-игры)), поэтому ошибка сети проверяется _после_ ожидания, по статусу в сторе; упасть `Promise.all` может только через `reels.spin` — при аборте. Третье: при ошибке сети фаза возвращает `idle`, и это **молчаливый откат** — барабаны просто останавливаются на случайных символах, игроку ничего не сообщается; `result.error` при этом лежит в сторе, но никем не читается, а следующий `run` его перезапишет.

**[result.ts](src/flow/phases/result.ts)** — показ результата: взять `spinStore.result.value`, дождаться `await reels.land(result, signal)` — фаза _обязана_ дождаться конца анимации, поэтому команда вниз идёт вызовом метода, — объявить `spin:landed` и вернуться в `idle`.

Тонкость на границе фаз: `spinning` кладёт результат в стор, `result` достаёт его оттуда — эта связь нигде не выражена типом. Проверяется только наличие `value`, а не статус запроса; после первого успешного раунда в `value` всегда лежит _какое-то_ значение, так что защитная проверка спасает лишь от запуска `result` на абсолютно свежем сторе. Контракт держится на порядке переходов — это стоит помнить, меняя граф фаз.

На этих трёх файлах хорошо видно распределение ролей: **фазы — единственные, кто пишет в сторы и эмитит игровые события.** Вся «история раунда» читается по этим трём файлам сверху вниз, без заглядывания в контроллеры.

### 3.5 stores — состояние игры

**[spin-store.ts](src/stores/spin-store.ts)** — состояние раунда, MobX-стор в 40 строк: `phase`, `bet`, `result: AsyncValue<SpinResult>`, `fatalError`; computed `canSpin` (можно крутить только в `idle`); сеттеры-actions. Все наблюдаемые члены размечены декораторами у объявления + `makeObservable(this)` в конструкторе (см. [2.2](#22-реактивность-mobx)); `result` и `fatalError` — `@observable.ref`. Экземпляром владеет app-контейнер, поэтому стор живёт всё время работы вкладки: ставка переживает уход со страницы игры и возврат. Писатели — фазы и движок автомата, читатели — кнопка (через `reaction`) и будущий React-UI.

Тонкость: поле `fatalError` заполняется при крахе автомата (`onError` движка), но пока ничем не читается — ни UI, ни канвасом. Вместе с поведением движка (см. [2.4](#24-конечный-автомат)) это означает: упавший автомат оставляет игру в последней фазе с выключенной кнопкой и без индикации проблемы.

**[stores/utils/](src/stores/utils/)** — классы-хелперы для асинхронности в сторах, по классу на файл.

**[async-value.ts](src/stores/utils/async-value.ts)** — стандартная обвязка асинхронного значения: `value` / `status` (`idle → loading → success | error`) / `error` + computed `isLoading`. Метод `run(task)` принимает функцию-запрос и сам ведёт статусы (реализация на `flow` — разобрана в [2.2](#22-реактивность-mobx)). Смысл класса — единый синтаксис для фетчей и мутаций в любом сторе: `result.run(() => api.sendSpin(bet, signal))` вместо ручных полей `loading`/`error` в каждом сторе заново.

У `run` два свойства, которые надо знать:

- **Он никогда не реджектится.** Ошибка запроса ловится внутри и складывается в `status`/`error`. На это опирается фаза `spinning`: `Promise.all([result.run(...), reels.spin(...)])` не упадёт из-за сети — сетевую ошибку фаза после ожидания читает из стора как данные.
- **Он не защищён от конкурентных запусков.** Два перекрывающихся `run` пишут в одни поля наперегонки: медленный первый ответ может перезаписать быстрый второй. Сейчас это не возникает — единственный писатель (фазы) запускает по одному запросу за раунд, — но при использовании класса вне этой дисциплины ограничение станет актуальным.

**[async-stream.ts](src/stores/utils/async-stream.ts)** — то же для push-подписок: `start(subscribeFn)` подписывается и складывает каждое пришедшее значение в observable `value` (через `runInAction` — колбэк приходит извне action), `stop()` отписывается. Пока ни одним стором не используется — это задел под серверные push-сообщения (обновления баланса, оповещения), инфраструктура для которых уже есть и в транспорте (`subscribe`), и в моках (`push`).

### 3.6 game — PIXI-слой

**[utils.ts](src/game/utils.ts)** — `waitTicks`, «пауза в игровом времени»: промис, который резолвится, когда тикер накопил `durationMs` миллисекунд (суммируя `deltaMS` кадров). Принимает `signal` — при аборте снимает свою функцию с тикера и реджектится. Устроен по тому же settle-паттерну, что и `waitFor`: единая точка завершения, которая сначала убирает за собой (снять с тикера, снять слушатель abort), потом резолвит или реджектит. Зачем он вместо `setTimeout` — см. [2.6](#26-pixi-и-мост-с-react).

**[animations/reel-animation.ts](src/game/animations/reel-animation.ts)** — класс анимации, заглушка будущих барабанов. Не наследует ничего: у него есть `view` (Container с `Graphics`-подложкой и `Text`-табло) и три смысловых метода:

- `spin(signal)` — «крутиться»: вешает на тикер функцию, каждые 60 мс тикерного времени подменяющую символы случайными, ждёт `waitTicks(900)` и в `finally` гарантированно снимает функцию с тикера (даже при аборте).
- `land(result, signal)` — «приземлиться»: показать присланные сервером символы и выдержать паузу 350 мс, чтобы фаза не проскочила показ мгновенно.
- `highlight(result)` — подсветить выигрыш. Единственный синхронный метод — и это не случайно: `spin`/`land` — _команды_, которых дожидается фаза (промис), а `highlight` — _реакция на уже случившееся событие_, ждать её никому не нужно.

Когда дойдёт до Spine, перепишется только внутренность этого класса — сигнатуры методов и промисы останутся, и ни контроллер, ни фазы не заметят подмены.

**[controllers/reels-controller.ts](src/game/controllers/reels-controller.ts)** — контроллер барабанов: наследует `Container` (он — узел сцены), создаёт `ReelAnimation`, добавляет её view себе в дети. Роль контроллера — **посредник между миром игры и анимацией**: он держит подписки на события (`spin:landed` → `highlight`), прокидывает команды с промисами (`spin`, `land`) и отвечает за позиционирование на экране (`layout`). Анимация благодаря этому остаётся чистой: ни эмиттера, ни сторов, ни экранных координат она не знает.

**[controllers/spin-button.ts](src/game/controllers/spin-button.ts)** — кнопка SPIN, самый показательный файл проекта: в 70 строках сходятся все три механизма связи.

- **Вверх — событие:** тап по кнопке → `emit('ui:spinRequested', { bet: this.spinStore.bet })`. Кнопка не знает, что случится дальше, — она лишь объявила факт.
- **Вниз — реактивность:** `reaction(() => this.spinStore.canSpin, ...)` включает и выключает кнопку вслед за фазой. Заметь: никто не «командует» кнопке выключиться — она сама следит за состоянием.
- **Чтение стора:** ставку кнопка _читает_ из стора (это разрешено), но не пишет — запись ставки делает фаза `idle`. Сам стор кнопке приносит контейнер (`@inject(TOKENS.SpinStore)`): чьё именно состояние она читает — решает композиция.

**Границу слоя** держит правило: `game/*` не импортирует `flow/*`. Контроллеры не знают ни про фазы, ни про сценарий раунда — только события, сторы и собственные анимации. Именно поэтому автомат можно переписать, не открыв ни одного файла в `game/`.

### 3.7 app — composition root и хост игры

Слой `app/` лежит над остальными: только здесь можно зависеть от всех сразу. Композицию держат **два файла в `app/`** — `container.ts` и `game-container.ts`. Третий участник, `game-root.ts` (хост жизненного цикла), живёт в `game/`: граф он не собирает, а оркеструет уже собранные контейнеры — поэтому разбираем его здесь, рядом с ними.

**[container.ts](src/app/container.ts)** — app-контейнер, биндинги уровня приложения (транспорт, api, эмиттер, стор, транзиентный `GameRoot`, фабрика game-контейнера). Разобран в [2.5](#25-dependency-injection). Единственный module-scope синглтон проекта.

**[game-container.ts](src/app/game-container.ts)** — фабрика child-контейнера на один маунт: константы `Application`/`Ticker`, контроллеры с деактивациями-`destroy`, биндинг автомата. Именно здесь комплектуется `PhaseContext` и подключаются колбэки движка к стору: `onPhaseChange → spinStore.setPhase`, `onError → spinStore.setFatalError`. Состав игрового графа читается по этому файлу сверху вниз.

**[game-root.ts](src/game/game-root.ts)** — **хост жизненного цикла**. Сборкой он больше не занимается (это дело контейнеров) — за ним осталось то, чего контейнер сделать не может: асинхронный PIXI-init, мост с DOM, layout и _порядок_ рождения и смерти объектов. MobX в нём нет — наблюдаемого состояния он не хранит, все поля (`Application`, контроллеры, контейнер, токен `pending`) — тяжёлые нереактивные объекты. Забинжен transient: экземпляр на каждый маунт резолвит страница, время его жизни совпадает со временем жизни роута.

Его `mount(container)`:

1. создаёт `Application` и проходит асинхронный `init` с защитой от гонки StrictMode (токен `pending`, разобран в [2.6](#26-pixi-и-мост-с-react));
2. вставляет канвас в DOM и создаёт game-контейнер через инъецированную фабрику (`Application` и `Ticker` одалживаются контейнеру константами);
3. достаёт контроллеры (`get`) — контейнер сам разрешает их зависимости — и добавляет на сцену;
4. расставляет всё по экрану (`layout`) и подписывает его на ресайз рендерера;
5. достаёт автомат (`get(TOKENS.Fsm)`) — биндинг собирает его вместе с контекстом фаз — и запускает `void fsm.start()`.

`unmount()` разбирает игру: сбросить `pending` (чтобы недоехавший `mount` понял, что устарел) → снять слушатель ресайза → цепочка `unbind`: автомат (деактивация делает `dispose()`, абортя все ожидания), затем контроллеры (деактивации делают `destroy()`, снимая подписки) → отпустить контейнер → уничтожить `Application` вместе с канвасом и WebGL-контекстом (её создал хост — он и уничтожает). Подробный каскад — в [главе 5](#5-жизненный-цикл-маунт-и-анмаунт-игры).

### 3.8 React-обвязка

Кратко — игровой логики здесь нет.

**[main.tsx](src/main.tsx)** — вход: запустить MSW (только DEV, динамическим импортом) и лишь затем отрендерить `<App/>`. **[app/](src/app/)** — `StrictMode → RouterProvider`; роутер объявляет три страницы (`/`, `/game`, `*`), каждая грузится лениво через `lazy` — код игры не попадает в бандл лендинга. **[Layout](src/components/Layout/index.tsx)** — шапка с логотипом и `<Outlet/>` для страниц. **[GamePage](src/pages/game/index.tsx)** — мост React↔PIXI ([2.6](#26-pixi-и-мост-с-react)): div + `useEffect`, который резолвит `GameRoot` из app-контейнера (страница — точка входа, ей это разрешено) и разбирает его при уходе.

**[MainPage](src/pages/main/index.tsx)** — лендинг: заголовок, кнопка «Играть» и [BackgroundCanvas](src/pages/main/BackgroundCanvas/index.tsx) — отдельное маленькое PIXI-приложение с фоном из размытых дрейфующих пятен (`mountBackground` и `createBlobTexture` в [pages/main/utils.ts](src/pages/main/utils.ts)). Устроен он по тем же канонам, что и игра, только в функциональном стиле: защита от StrictMode локальным флагом `disposed`, движение — накоплением `deltaMS` в тикере, полный teardown с уничтожением текстуры. Единственная особенность: при `prefers-reduced-motion` тикер-цикл вообще не добавляется — фон остаётся статичной картинкой. Игровой архитектуры фон не касается: ни сторов, ни событий, ни автомата в нём нет.

## 4. Игровой флоу: трассировка одного спина

Главная глава дока: один полный раунд, от клика до готовности к следующему клику, со всеми участниками. На этом пути видны все связи из [карты системы](#1-карта-системы) в действии.

**1. Исходное положение.** Автомат стоит в фазе `idle` и спит на `await waitFor(emitter, 'ui:spinRequested')`. В эмиттере — две подписки: одноразовая от этого ожидания и постоянная от `ReelsController` на `spin:landed`. Больше не происходит ничего: ни проверок в цикле, ни таймеров. Кнопка активна (`canSpin === true`, потому что `phase === 'idle'`).

**2. Клик.** PIXI ловит тап по кнопке и вызывает `handleTap`. Кнопка читает текущую ставку из стора и объявляет: `emit('ui:spinRequested', { bet: 10 })`. На этом её участие закончено — она не знает ни про автомат, ни про сеть.

**3. Пробуждение автомата.** `emit` синхронно вызывает подписчика — колбэк внутри `waitFor`. Тот снимает свою подписку (событие одноразовое) и резолвит промис. Фаза `idle` просыпается, записывает ставку в стор (`setBet` — первая запись в стор за раунд) и возвращает `'spinning'`.

**4. Переход.** Движок получает имя следующей фазы, вызывает `onPhaseChange('spinning')` → `spinStore.setPhase('spinning')`. Тут же срабатывает MobX-цепочка: `phase` изменился → computed `canSpin` стал `false` → `reaction` в кнопке выключает её (`eventMode = 'none'`, полупрозрачность). Игрок больше не может кликнуть, пока раунд не завершится.

**5. Фаза spinning: развилка.** Фаза объявляет `spin:started` (слушателей пока нет — событие на вырост) и запускает **параллельно** два процесса, дожидаясь обоих через `Promise.all`:

- **Сеть.** `spinStore.result.run(() => api.sendSpin(bet, signal))`: статус в сторе становится `loading`, транспорт генерирует id (`nanoid()`), кладёт deferred-промис в `pending`, шлёт `{ id, type: 'spin', payload: { bet: 10 } }`. Service Worker перехватывает, мок бросает три случайных символа, считает выигрыш и отвечает `{ id, type: 'spinResult', payload: { symbols: [3,3,3], win: 100 } }`. Транспорт находит запись по id, прогоняет payload через zod-схему и резолвит промис запроса. `AsyncValue` дописывает: `value` = результат, `status = 'success'`.
- **Анимация.** `reels.spin(signal)` → `ReelAnimation.spin`: на тикер вешается мерцание символов, промис держится 900 мс тикерного времени.

Мок отвечает почти мгновенно, поэтому реальная длительность фазы — это длительность анимации. С настоящим сервером порядок завершения может быть любым — `Promise.all` этим не интересуется, ему нужны оба.

**6. Проверка исхода.** Фаза смотрит `spinStore.result.status`. Успех → вернуть `'result'`. Ошибка → вернуть `'idle'` (об этой ветке — ниже).

**7. Фаза result: приземление.** Фаза берёт результат из стора и командует `await reels.land(result, signal)` — прямой вызов метода, не событие, потому что фазе **нужно дождаться** конца показа. Табло показывает серверные символы и держит паузу 350 мс.

**8. Объявление результата.** Только после того как приземление отыграло, фаза объявляет `spin:landed`. Подписчик — `ReelsController` — синхронно вызывает `highlight`: выигрыш подсвечивается цветом. Именно сюда потом подключится звук выигрыша — подпиской, без единой правки фазы.

**9. Замыкание круга.** Фаза возвращает `'idle'`. Движок: `setPhase('idle')` → `canSpin = true` → реакция включает кнопку. Фаза `idle` снова засыпает на `waitFor`. Система вернулась в исходное положение — счётчики подписок те же, что до раунда (проверяется в консоли: `appContainer.get(TOKENS.GameEmitter).listenerCounts()`).

В DEV-консоли раунд выглядит как три строки трассировки эмиттера — это самый быстрый способ убедиться, что последовательность правильная:

```
[event] ui:spinRequested { bet: 10 }
[event] spin:started     { bet: 10 }
[event] spin:landed      { symbols: [3, 3, 3], win: 100 }
```

### Ветка: сеть ответила ошибкой

`AsyncValue.run` не реджектится — ошибка (таймаут сторожа, обрыв сокета, ответ сервера с `error`, payload, не прошедший zod-валидацию) складывается в `result.error`, статус становится `'error'`. `Promise.all` при этом спокойно дожидается анимацию: барабаны докручивают свои 900 мс. Затем фаза видит `status === 'error'` и возвращается в `idle` — кнопка включается, можно пробовать снова. Показа результата не происходит (его и нет), `spin:landed` не объявляется. Игроку при этом ничего не сообщается — барабаны просто остановились на случайных символах; `result.error` лежит в сторе непрочитанным, пока следующий `run` его не перезапишет.

### Кто читает и кто пишет: сводка за раунд

| Момент          | Пишет в стор                        | Читает из стора                    |
| --------------- | ----------------------------------- | ---------------------------------- |
| Клик            | —                                   | кнопка: `bet`                      |
| Вход в фазу     | движок: `phase`                     | реакция кнопки: `canSpin`          |
| idle → spinning | фаза idle: `bet`                    | —                                  |
| spinning        | AsyncValue (внутри стора): `result` | фаза: `bet`, потом `result.status` |
| result          | —                                   | фаза: `result.value`               |

За весь раунд — ни одной записи из контроллеров, анимаций или React: инвариант «единственный писатель» здесь виден наглядно.

## 5. Жизненный цикл: маунт и анмаунт игры

### Граф фаз

Все переходы автомата, один списком:

- `idle → spinning` — получено событие `ui:spinRequested`;
- `spinning → result` — ответ сервера получен и анимация докручена;
- `spinning → idle` — сеть ответила ошибкой;
- `result → idle` — показ результата завершён;
- из **любой** фазы — остановка: `fsm.dispose()` при уходе со страницы абортит сигнал, текущее ожидание реджектится, движок распознаёт отмену и тихо завершает цикл.

### Маунт

Всё происходит в `GameRoot.mount(container)` — экземпляр страница взяла из app-контейнера, — строго по порядку (детали шагов — в [3.7](#37-app--composition-root-и-хост-игры) и [2.6](#26-pixi-и-мост-с-react)):

1. `new Application()` + `await app.init(...)` — с проверкой токена `pending` после `await`;
2. канвас — в DOM; создаётся game-контейнер (child), контроллеры достаются `get()`-ами — зависимости им разрешает контейнер — и добавляются на сцену;
3. `layout()` + подписка на ресайз;
4. `get(TOKENS.Fsm)` — биндинг собирает автомат с контекстом фаз — и запуск `void fsm.start()`: цикл фаз начинает работать, `idle` засыпает на `waitFor`.

В StrictMode эта последовательность отрабатывает дважды: React вызывает mount → cleanup → mount (страница резолвит **два** транзиентных `GameRoot`, по одному на попытку). Первый `mount` зависает на `await init`, за это время `unmount` сбрасывает `pending`, второй `mount` начинает свою попытку. Когда `init` первого завершается, тот видит `this.pending !== app`, уничтожает _свой_ app и выходит — до создания контейнера и графа он не дошёл. В итоге живым остаётся ровно один экземпляр всего — приложение, контейнер, контроллеры, автомат.

### Анмаунт

`unmount()` разбирает игру в порядке, обратном сборке. «Как умирает» каждый объект, объявлено в его биндинге (`onDeactivation` в [game-container.ts](src/app/game-container.ts)); за хостом остаётся **порядок** — цепочка синхронных `unbind()`. Каскад отмены стоит проследить целиком. Допустим, игрок ушёл со страницы прямо посреди вращения:

1. Снимается слушатель ресайза.
2. `unbind(TOKENS.Fsm)` → деактивация вызывает `fsm.dispose()` → `AbortController.abort()`. Сигнал един для всех ожиданий, поэтому реджектятся разом: `waitTicks` внутри `ReelAnimation.spin` (а его `finally` снимает мерцание с тикера — анимация прибирает за собой даже при отмене), сетевой запрос в транспорте, а с ними и `Promise.all` фазы `spinning`. Исключение долетает до `catch` движка; тот видит `signal.aborted` — это отмена, не ошибка — и молча завершает цикл, `onError` не вызывается.
3. `unbind(TOKENS.ReelsController)`, `unbind(TOKENS.SpinButton)` → деактивации вызывают `destroy({ children: true })` — мешки disposers опустошены: отписки от эмиттера и MobX-реакции сняты, счётчики слушателей app-эмиттера вернулись к нулю.
4. Ссылка на game-контейнер отпускается — кэш его синглтонов уходит под сборщик мусора.
5. `app.destroy(true, { children: true })` — уничтожены сцена, тикер, канвас и WebGL-контекст. `Application` создал хост — он и уничтожает; контейнер её только одалживал (PIXI-`destroy` идемпотентен, поэтому каскад `children: true` спокойно проходит по уже уничтоженным контроллерам).

После этого от game-уровня не остаётся ничего: ни подписки, ни таймера, ни GPU-ресурса. **App-уровень живёт дальше**: транспорт, эмиттер и стор в app-контейнере переживают уход — ставка при возврате та же. Повторный заход на `/game` строит игровой граф с нуля в свежем child-контейнере — и это осознанное решение: секунда, сэкономленная на повторном маунте, не оправдывает утечек, которыми грозит «замороженная» игра, оставленная жить в памяти.
