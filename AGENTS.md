# Инструкции Codex для pixi-demos

## Основной источник

- Перед планированием, ревью или изменением кода полностью прочитай `CLAUDE.md`. Это основной документ
  с архитектурой, командами, направлением зависимостей и код-стайлом проекта.
- Этот файл дополняет `CLAUDE.md` договорённостями из памяти Claude. При расхождении сообщи об этом
  разработчику; не исправляй документы или код молча.
- `CLAUDE.md` меняется только после предварительного обсуждения конкретной правки.
- Комментарии и документация проекта пишутся по-русски. Строки UI, сообщения об ошибках и уведомления
  для пользователя пишутся по-английски.

## Общение и инженерный текст

- Пиши прямо, кратко и предметно. Не используй метафоры, клише, пафос, разговорный сленг,
  риторические дихотомии вида «X, а не Y» и одушевление программ, инструментов или ассетов.
- Не придумывай слова и кальки. Используй обычный русский язык или точное название API и класса.
- У каждого описанного действия указывай субъект и объект. Формулировка должна сообщать фактическое
  поведение, причину или ограничение.
- При выборе решения показывай существенные альтернативы и аргументы. Не представляй спорный вариант
  как единственно допустимый.

## Работа с репозиторием

- Не выполняй `git commit`, `git push`, создание PR, публикацию или деплой без отдельного прямого
  запроса разработчика. Согласование плана и выполнение правок в рабочем дереве такого разрешения не дают.
- Сохраняй существующие изменения в рабочем дереве. Не возвращай удалённые или отредактированные
  разработчиком комментарии.
- Перед архитектурной рекомендацией проверь соседние слои, доменные типы, существующие тесты и способ,
  которым тесты достигают кода: через настоящую реализацию или дублёры.
- Перед введением маркера вроде `null` или `undefined` проверь его текущее доменное значение.
- Если повторная проверка меняет ранее согласованную рекомендацию, скажи об этом прямо и снова вынеси
  изменившийся выбор на обсуждение.

## Тестирование

- Добавляй тест, когда он проверяет отношение между значениями, инвариант, переход состояния,
  обработку ошибки или пользовательский сценарий, которые не выражаются системой типов.
- Если требование можно надёжно выразить типом или правилом линтера, усиливай статическую проверку.
- Интеграционные тесты должны проверять бизнес-сценарии. E2E покрывают критические пользовательские пути
  в окружении, близком к продакшену.
- Тестируй публичный API владеющего класса. Не открывай приватные методы ради тестов и не закрепляй
  внутреннюю структуру без поведенческой причины.
- Не тестируй внутреннюю математику серверных моков. Их детерминизм нужен для воспроизводимых сценариев.
- Тесты лежат в `tests/` соответствующего пакета, общая оснастка — в `tests/setup/`, E2E — в `e2e/`.

## Документация библиотек

- Для документации самостоятельных модулей используй порядок: введение, обзор, быстрый старт,
  руководства по модулям, механики, API по сущностям, адаптер, примеры, словарь.
- Отделяй API библиотеки от интеграции игры. FSM, стор, DI, эмиттер и фазы показывай в примерах как
  один из вариантов интеграции.
- Описывай композицию модулей и все публичные точки настройки. Не предлагай правку ядра как способ
  настройки библиотеки.
- Словарь располагается в конце; один термин занимает одну строку. Если термин уже описан в таблице,
  словарь ссылается на соответствующую строку.
- Сигнатуры и утверждения о поведении сверяй с исходниками. Терминология документации, JSDoc и тестов
  должна совпадать.
- Для рил-машины используй термины `stagger`, «перенос слота», «приведение позиции к диапазону ленты»
  и название «Рил-машина».

## Актуальность памяти

- Текущий статус и устройство проекта бери из `CLAUDE.md` и кода. Старый роадмап toybox и заметка о
  состоянии сборки после переписывания истории являются историческим контекстом и не определяют
  текущее поведение.
